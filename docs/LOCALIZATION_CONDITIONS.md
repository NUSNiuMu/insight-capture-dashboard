# 三相机定位条件与待讨论项

本页对应 `codex/stream-startup-recovery` 的本地修改，不代表客户设备已升级。

## 已解除的联动

| 原行为 | 当前行为 |
| --- | --- |
| 头部初始化等待两腕 CameraInfo、TF | 头部仅用自己的双目参数初始化；两腕分别注册，B 可先于 A 加入 |
| 任一 SDK 异常状态清除对应定位，头部异常清空全图 | 保留地图与修正，暂停异常设备的新图像处理和坐标发布；其他已定位设备继续 |
| VIO 接收中断超过 2 秒就清除定位 | 源时间连续则保留地图与修正，只清除跨断流的速度估计；时钟偏移变化时重新同步本机时钟 |
| 任一相机前缀下的 TF 数值变化都重建地图 | 比较实际使用的相机模型与中心变换；无关 TF、等价四元数不触发重建，腕部参数变化只重配该腕部 |
| 所有腕部定位必须有两个参考帧在 1 cm、1° 内一致 | 从通过现有几何检查的候选中选择解；单参考帧可用于普通定位，双参考帧共识用于标记可靠重定位 |
| 未取得插值位姿也推进发布游标 | 成功发布后才推进；尚可补齐的末端位姿可在后续发布周期处理 |
| 校准接口和手机按钮要求三机同时就绪 | 校准启动只要求头部就绪；三机完整录制的输入检查保持独立 |
| 用墙钟时间排除重置前图像 | 改用各设备原生时间戳的重置水位，避免时钟重同步后被旧墙钟水位持续阻塞 |

没有增加替代定位算法、默认外参或预测坐标输出路径。

## 仍保留的条件

| 条件 | 当前行为及讨论方向 |
| --- | --- |
| SDK 源时间戳倒退 | 仍保守视作设备重启；腕部清除本机定位，头部清空地图。时钟倒退不一定证明坐标系已重置，后续需讨论如何进一步区分 |
| SDK 状态枚举 | 本机仍须 `TRACKING` 或 `TRACKING_STATIC` 才处理新图像、接收图像位姿及发布新坐标；异常期间保留历史状态，不外推补造轨迹 |
| 原始 VIO 时钟初始化 | 仍收集 100 条消息；首次启动和时钟重同步期间该设备等待 |
| 图像与位姿时间条件 | 双目差不超过 2 ms；图像位姿最多等待 100 ms；插值两侧各不超过 50 ms，缓存范围外不外推 |
| 地标与几何条件 | 腕部至少 10 个成熟点、至少 4 个网格、3 px 残差、几何条件比不低于 1e-6；地图点至少 3 帧观测并完成优化；普通重拟合要求 50% 支持，地图更新重拟合要求 80% |
| 头部优化 | 头部地图位姿优化仍要求 40 个成熟点；不足时跳过该优化，首帧建图和位姿初始化不以此作为启动条件 |
| 大幅视觉纠偏 | 已初始化后超过 5 cm 的修正仍须可靠重定位确认；小修正继续 EKF，输出沿用现有连续注入 |
| SDK 平移修订 | 仍有“5 cm 加 IMU 运动界限”检测和速度外推抵消逻辑；本轮仅避免沿用断流前的速度，未删除该逻辑 |
| 处理频率 | 头部图像处理 2 Hz、腕部 4 Hz、位姿输出目标 30 Hz；队列只保留各视角最新待处理帧 |
| 展示新鲜度 | 全局位姿默认超过 2 秒未更新就隐藏模型；是否改为保留最后模型并明确标注陈旧，待讨论 |
| 外部服务和原始格式 | 仍依赖推理健康状态、原生建图 socket、合法 CameraInfo/TF；灰度建图支持 mono8、8UC1、NV12，跨设备匹配要求相同图像尺寸 |

SDK 时钟未倒退、但内部坐标系发生重置的情况，不能仅凭本次状态保留策略宣称已经识别。真实头部几何变化仍需重建地图；首次世界地图仍由头部建立。

## 验证范围

相关检查、原生 C++ 单/双参考帧求解、受控 ROS 输入的头部独立启动/腕部陆续加入/断流和失跟恢复，以及手机真实页面按钮操作均有记录。静态、运动旧包采用同一冻结特征和 VIO 做原生几何 A/B 回放，统计校准后的共同样本；该回放不模拟当前 SDK 图像位姿链路、在线队列或 EKF 延迟，不能作为线上最终误差结论。
