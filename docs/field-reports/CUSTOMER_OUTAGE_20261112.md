录制中与修正后测试均确认 `iptables -S` 与注入前一致。第一次成功的空闲测试已确认临时链清除，但比较 `iptables-save` 时把变化的计数器当成规则变化；该布尔值不能用来证明规则不一致。另有两次测试工具预检查失败，没有注入故障，不计入产品结果。

## 修复的诊断错误

旧 `ImagePipeline.clock_status()` 把图像过期和真实时间戳偏差合为失败。最后一帧与接收时钟仅差 -29.049 ms，却因 age > 2 秒提示重启相机采集进程。

- 状态分为 `ready` / `missing` / `stale` / `invalid`。旧样本不能诊断当前相机时钟。
- 未取得新鲜图像，报告 `image_clock_unavailable`；只有新鲜样本确实超出原有时间范围，才报告 `image_clock_invalid`。
- 页面设备状态对真实时间戳错误显示异常，不再与“已就绪”矛盾。
- 历史详情将内部标签翻译为“左腕相机图像曾中断，本条需要复检”。

图像新鲜度 2 秒、源与接收时钟范围 [-2, +1] 秒及原有 NTP / 存储阈值均未改变。错误分类修正没有解除缺图像的开始限制。

## 未解决：恢复时出现空图像消息

空消息时间 `1794483688814496045 ns`，解除故障后约 2.06 秒。ROS bag 读取器返回长度 0，ROS 反序列化失败；依据 https://mcap.dev/spec 直接扫描原文件，独立确认同一条 Message 载荷为空。

直接扫描定位：文件 Chunk 偏移 `721259656`，Chunk 内记录偏移 `531573`，channel 5，Message 内容长度 22 字节（只有容器字段、无 ROS 载荷）。文件共 1,368 个未压缩 Chunk，无可用 Chunk CRC；未宣称 CRC 校验通过。

完整性 API 实际运行约 3.87 秒，正确报告左腕图像 `invalid_source_stamps = 1`、约 14.067 秒间隔，整包检查失败。没有删除空消息或用接收时间替代无效源时间。

**根因尚未确定。** 当前证据定位到写入文件的消息层，不能断言是相机发布、DDS 接收或录制器哪一层生成。下一步需要同一恢复事件的分层消息长度证据。

头部 VIO 98.44 Hz 对配置基准 99 Hz 有 0.54% 数量短缺，仍触发现有检查；不能从本轮推导为头部链路丢包。内核接收错误计数为零也不能证明无数据缺失，本次故障由防火墙显式丢弃造成。
